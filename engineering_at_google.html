Software Engineering at Google

An Interactive Playbook & Educational Resource

The Central Thesis

Google defines Software Engineering as: "Programming integrated with the constraints of Time, Scale, and Trade-offs."

This playbook captures the organizational practices, cultural pillars, processes, and tools that enable Google to build and maintain software running for decades, worked on by tens of thousands of engineers, spanning a monorepo containing billions of lines of code.

Time & Change

Programming is about writing code. Software Engineering is about maintaining that code over its lifetime. How will a piece of code behave 10 or 20 years from now when libraries, compilers, operating systems, and personnel change?

Scale & Efficiency

Google's systems must scale not just in traffic, but in human organization. Policies must scale sub-linearly: if doubling the size of your codebase or engineering staff requires doubling your build times or manually rewriting client code, the organization will fail.

Part I: Thesis

Chapter 1: What Is Software Engineering?

Google draws a stark line between programming (the act of producing code) and software engineering (programming plus time and team scale). If you are writing a script that will be run once and discarded, you are programming. If you are writing code that will survive upgrade cycles, new maintainers, and library updates, you are doing software engineering.

The Three Key Dimensions

  • Time: Codebases must survive changes in compilers, operating systems, dependencies, and business needs. Upgrading a compiler should be a routine, automated process.
  • Scale: Organization scale (number of engineers, repositories) and execution scale (servers, database sizes) demand automation. Policies that require manual work from every developer do not scale.
  • Trade-offs: Every technical decision carries costs (compute, developer hours, maintenance). Google prioritizes making decisions based on data rather than developer emotion.
Case Study: Compiler Upgrades at Google Scale

At Google's scale, manual compiler upgrades are impossible. If a compiler upgrade introduces a breaking change in a language feature, manually modifying tens of thousands of files across different teams would halt feature development for months. Google instead invested in building automated code transformation tools. Their infrastructure parses the entire monorepo into an Abstract Syntax Tree (AST), identifies pattern violations, automatically applies the upgrade refactorings across all repositories, and commits the changes globally.

Shift-Left Philosophy

The "Shift-Left" principle dictates that bugs, security vulnerabilities, and design flaws should be caught as early in the development lifecycle as possible. Finding a bug during local editing costs minutes; finding it during staging costs hours; finding it in production can cost millions of dollars and compromise user trust. Google incorporates static analysis, style linters, and unit tests directly into the developer's edit loop (inside the IDE and code review tool) to enforce quality immediately.

🎓 Educator Discussion Prompt:

Ask students: If you write a piece of code that runs in production for 10 years without modifications, did you write programming code or software engineering code? Discuss the role of maintenance, automated updates, and external API dependency shifts during those 10 years.

Part II: Culture — Working on Teams

Chapter 2: How to Work Well on Teams

Software development is a team sport. Google actively rejects the "Genius Myth"—the idea that great software is written by brilliant lone wolves in dark rooms. Hiding your code out of fear of judgment or mistake slows down innovation, creates single points of failure (low Bus Factor), and prevents early feedback.

The Three Pillars of Social Interaction

  1. Humility: You are not the center of the universe. You do not know everything. You are open to self-improvement and learning from others.
  2. Respect: Treat others with kindness and value their abilities and contributions. Assume positive intent.
  3. Trust: Believe that others are competent and want to do a good job. Give them the autonomy to succeed.

Blameless Post-Mortems

When an outage or mistake occurs, the focus must be on **fixing the system and process**, not assigning blame to individuals. If engineers fear being blamed, they will hide mistakes, leading to catastrophic systemic failures later.

Case Study: Google's Outage Culture

Google maintains a repository of all post-mortems. When a developer accidentally runs a script that causes a massive service outage, their name is omitted or kept neutral. Instead, the post-mortem documents: Why did the script have production write permissions without an approval step? Why did the monitoring system take 15 minutes to alert? How can we modify the deployment tool to prevent this class of errors? This fosters a culture where mistakes are treated as debugging input for organizational processes.

🎓 Class Exercise:

Conduct a mock "Blameless Post-Mortem" session. Present a scenario where an engineer accidentally drops a production database table. Guide the team to focus on why the system allowed a single developer to run a destructive query without guardrails rather than blaming the developer.

Part II: Culture — Knowledge Sharing

Chapter 3: Knowledge Sharing

An engineering organization must scale its collective knowledge to survive. Google fosters psychological safety so developers feel comfortable asking "stupid" questions. It uses several structures to scale knowledge:

Internal Q&A and Documentation

  • YAQS (Yet Another Q&A Service): An internal StackOverflow-like system where engineers can ask questions and vote on canonical answers. This reduces duplicate threads on mailing lists.
  • Google Go Links: A centralized shortcut redirect service (e.g., `go/readability`) that enables instant navigation to canonical documents.

The Readability Process

The **Readability Process** is a standardized mentorship system. To submit code in a specific language (e.g. C++), the code must be approved by someone with a "Readability" credential in that language. Engineers submit code changes to "Readability Arbiters" who comment not just on functional correctness, but on style, APIs, idioms, and design consistency. This process ensures that C++ written by an ads engineer looks identical to C++ written by a search engineer, facilitating massive developer mobility.

🎓 Discussion:

Discuss the pros and cons of Google's Readability process. Does it slow down feature velocity? How does it impact code quality and long-term maintainability when engineers switch teams?

Part II: Culture — Engineering for Equity

Chapter 4: Engineering for Equity

Google emphasizes that bias is the default in systems if diversity and inclusion are not actively designed. Software engineers must consciously build multicultural capacity, reject singular approaches, and actively challenge established processes to ensure products work equitably for everyone.

Algorithmic Bias and Inclusive Architecture

Systems learn from the data provided to them. If dataset representation is skewed, ML models fail for marginalized demographics. Engineers must audit training datasets for representation, test accessibility tools (screen readers, high-contrast themes), and evaluate how latency budgets affect users on slow mobile networks in developing countries.

🎓 Seminar Topic:

How do design choices (like default camera exposure algorithms or voice recognition accents) reflect systemic biases? How can teams systematically audit their products for equitable outcomes?

Part II: Culture — Leading Teams at Scale

Chapters 5 & 6: How to Lead a Team & Leading at Scale

Google distinguishes between Managers (who focus on people and career development) and Tech Leads (who focus on technical direction). Key leadership patterns include:

Servant Leadership

Traditional command-and-control management fails in creative software engineering. Servant leaders focus on:

  • Removing organizational roadblocks and administrative friction.
  • Fostering career goals and technical growth for individual contributors.
  • Maintaining team health and psychological safety.

Three Rules for Scaling Leadership

  1. Always Be Deciding: Make decisions in conditions of ambiguity. Use data to evaluate trade-offs, commit to a path, and establish rapid feedback loops to course-correct.
  2. Always Be Leaving: Build a "self-driving" team. Document processes, delegate responsibilities, and mentor junior engineers so they can make high-level decisions. A team that breaks down when the leader is away represents a leadership failure.
  3. Always Be Scaling: Shift time allocation from urgent issues (firefighting) to important structural changes (process improvement, documentation, architecture refactorings).
🎓 Scenario Roleplay:

Assign one student as a Tech Lead and another as a manager. Simulate resolving a conflict where a senior developer wants to rebuild a core service using a new language, but the business requires stabilizing the existing codebase.

Part II: Culture — Measuring Productivity

Chapter 7: Measuring Engineering Productivity

Measuring developer productivity is notoriously difficult. Metrics like "lines of code" or "number of commits" are harmful counter-indicators. Google uses the **GSM (Goals, Signals, Metrics)** framework:

The GSM Framework Mapped

GSM Component Definition Example Scenario
Goal The qualitative outcome desired (independent of how it's measured). "Ensure code reviews are completed quickly to prevent developer wait times."
Signal The observable behavior indicating if the goal is met. "Developers wait less time for reviewer comments on their PRs."
Metric The quantitative data points tracked using telemetry or surveys. "Median duration (hours) from PR submission to first review response."
🎓 Team Activity:

Have students define a GSM matrix for improving the quality of their university team projects. What goals matter, and how will they track signals without creating toxic metrics?

Part III: Processes — Style Guides & Rules

Chapter 8: Style Guides and Rules

Google enforces strict, standardized style guides across all languages. These rules aim to ensure that **any engineer can read any file in the monorepo and understand it easily**.

Guiding Principles for Rules

  • Avoid rules that are purely aesthetic preferences. Rules must have tangible benefits (safety, readability, tooling compatibility).
  • Enforce consistency using automated formatters (like `clang-format` or `gofmt`) rather than arguing during code reviews.
  • Limit features that are prone to bugs or hard for novices to understand (e.g., C++ template metaprogramming or complex operator overloading).

Style Arbiters

Style guides at Google are owned and updated by a small committee of experts called **Style Arbiters**. When a developer wants to change a style guide rule, they must propose it to the arbiters, proving with data that the change increases safety or improves code performance.

Part III: Processes — Code Review

Chapter 9: Code Review

Every single line of code checked into Google's monorepo must be reviewed by at least one other engineer. Google's review system enforces three conditions before submission:

The Code Review Checklist

  1. Ownership: At least one reviewer must be listed in the `OWNERS` file for the directory containing the modified files.
  2. LGTM (Looks Good To Me): A reviewer must check the code for technical correctness, logic errors, and test coverage.
  3. Readability: Someone with readability credentials must confirm the code conforms to the style guides.

Etiquette and PR Sizing

Google strongly advocates for **small changes** (ideally less than 200 lines). Small PRs compile faster, are reviewed in minutes, and help reviewers spot subtle logic bugs. In code reviews, reviewers should remain respectful, critique the code (not the coder), and clearly distinguish between blocker comments and optional style suggestions (e.g. prepending optional comments with `Nit:`).

Part III: Processes — Documentation

Chapter 10: Documentation

Google treats **documentation like code**. It is stored in version control alongside the source files, undergoes code reviews, and has clear ownership. The book covers:

Documentation as Code

Storing documentation in markdown files next to the source code (the "g3doc" system) has several benefits:

  • Documentation updates can be included in the same PR as the code modifications.
  • It undergoes standard code reviews by owners.
  • It scales naturally with the repository version control history.

Design Documents

Before writing major code features, Google engineers write **Design Docs**. These documents outline the problem statement, user requirements, proposed architecture, alternatives considered, security/privacy evaluations, and testing strategy. The design doc is shared with other teams to gather feedback early, preventing expensive refactoring later.

Part III: Processes — Testing & Test Doubles

Chapters 11-14: Automated Testing at Scale

Google maintains a massive automated testing pipeline. They classify tests not by boundaries, but by **size** (Small, Medium, Large) and **scope** (Unit, Integration, End-to-End).

The Test Size Matrix

Test Size Execution Speed Allowed Activities Hermeticity
Small Under 100ms No disk, no network, single process, no thread sleep. 100% Hermetic. Fast and predictable.
Medium Under 1s Disk writes, local databases, multi-threading. Hermetic to the machine (no external network).
Large Minutes External databases, production network calls, complex servers. Low. Prone to external infrastructure flakiness.

Fakes vs. Mocks

Google suggests using **Real Implementations** where possible. When dependencies are slow or touch external systems, they recommend using **Fakes** (lightweight, working implementations of a service, e.g. an in-memory database) over **Mocks** (non-working objects that record interactions). Overusing mocks couples test code directly to the implementation details, making refactoring extremely difficult and leading to false confidence.

Part III: Processes — Deprecation

Chapter 15: Deprecation

Maintaining obsolete systems is a hidden tax on engineering organizations. However, deprecation is difficult. Google holds that **the author of a change is responsible for migrating downstream users**, not the downstream users themselves. If you want to deprecate an API, you must write the tool or manually rewrite the client code to migrate them off your system.

Trunk-Based Migration Strategy

Because Google works on a monorepo, developers can run Large-Scale Changes (LSCs) that migrate thousands of usages of a deprecated API across the entire codebase in a single commit, rather than waiting for individual teams to schedule migrations in their backlogs.

Part IV: Tools & Infrastructure

Chapters 16-25: Infrastructure

Google uses a unified developer toolchain integrated with their monorepo. Key components include:

Piper (Centralized VCS)

Piper is Google's custom centralized version control system containing billions of files. Unlike git, Piper supports fine-grained file permissions and doesn't require cloning the entire history locally. Engineers work on the head of the repository (trunk-based development), which prevents merge debt and diamond dependency mismatch conflicts.

Bazel / Blaze (Hermetic Build System)

Blaze (open-sourced as Bazel) is a declarative build system that uses a custom language to define build targets and their precise dependency graphs. Because Blaze enforces **hermetic builds** (compilations cannot access the network or unannounced filesystem resources), build outputs are 100% deterministic. This allows Google to run a massive global build cache, serving pre-compiled binaries to developers instantly if the input files haven't changed.

Tricorder (Static Analysis Platform)

Tricorder is Google's static analysis platform. It integrates closely with Critique (the code review tool). When an engineer writes code, Tricorder runs hundreds of analyzers (lints, security scans, compiler warnings) in the background. It displays findings directly inside the code review UI, often offering a one-click "Fix" button that applies the suggested edit automatically.
